# CaseLens 项目上下文

## 一句话定位

CaseLens 是一个可审计的电商争议复核 Agent 与政策回归实验台：它收集案件证据、调用只读业务工具、检索争议发生时有效的政策、生成可引用的处理建议，并通过审批、受控执行和状态验证形成闭环。

## 项目为什么存在

普通知识库问答只能回答“政策是什么”，无法可靠完成“这个案件应如何处理”。

真实争议复核需要同时处理：

- 来自订单、支付、物流和消息等系统的分散证据；
- 用户主张与系统记录之间的冲突；
- 随时间变化的政策版本；
- 工具超时、缺失数据和重复请求；
- 退款等高风险副作用；
- 人工审批、执行验证和审计追踪。

CaseLens 研究的核心问题是：

> 如何让一个会操作业务系统的 Agent，在政策版本变化、证据冲突和工具异常情况下，仍然可验证、可审批、可回放？

## 工程作品目标

本项目应成为高质量、可公开演示和可复现的 AI 应用工程作品。

它需要证明的不只是“会调用模型 API”，而是能够把不稳定的模型能力建设成可控、可验证、可部署和可持续改进的系统。

项目展示应重点体现：

- 垂直工作流 Agent；
- 结构化输出和工具调用；
- 证据工程与时间敏感 RAG；
- Human-in-the-loop 和安全副作用；
- 失败恢复、审计 trace 与可观测性；
- baseline、回归评测和工程权衡。

## 目标用户

V0.1 的主要用户是电商平台的争议复核专员或风控运营人员。

系统是决策支持工具，不代替人类承担最终责任。低风险结论可以自动整理，高风险动作必须停下来等待授权。

## V0.1 案件范围

首版只覆盖四类争议：

1. 显示签收但用户声称未收到；
2. 重复扣款或退款未到账；
3. 退货时序争议；
4. 错发或商品损坏。

不得在 V0.1 中扩展到通用客服、完整电商售后或其他行业。

## 核心工作流

V0.1 的主链路为：

1. 加载案件及用户主张；
2. 判断需要哪些证据；
3. 调用订单、支付、物流和消息等只读工具；
4. 记录结构化事实、证据来源和工具 trace；
5. 根据争议发生时间过滤政策版本；
6. 在有效版本内检索相关条款；
7. 检测缺失信息和证据冲突；
8. 生成带政策引用的 `DecisionPacket`；
9. 根据风险级别请求人工审批；
10. 审批后执行模拟动作；
11. 重新读取业务状态并由 verifier 验证结果；
12. 保存完整运行记录供回放和评测。

## 为什么必须使用时间敏感 RAG

政策会更新，但历史案件必须按争议发生时有效的版本处理。

检索顺序固定为：

1. 根据 `effective_from` 和 `effective_to` 过滤有效政策版本；
2. 在候选条款内进行语义检索；
3. 返回条款 ID、版本、有效期和原文引用；
4. 禁止用新政策判断旧案件。

首版政策规模较小，可直接使用 NumPy 计算相似度，不引入独立向量数据库。

## 安全和可靠性原则

- 查询工具默认只读；
- 工具输入通过 Pydantic 校验；
- 未知工具必须拒绝；
- Agent 有最大步骤数和安全终止条件；
- 工具超时或失败必须成为显式结果；
- 模型输出解析失败时不得猜测补全；
- 退款等副作用必须经过后端规则和必要审批；
- 副作用使用幂等键避免重复执行；
- 执行成功以最终业务状态为准，而不是以模型声称成功为准；
- 每个结论都应能追溯到证据和政策条款。

## 评测方向

至少建立以下三组 baseline：

1. Rules-only；
2. LLM-only；
3. Hybrid：LLM + 工具 + 时间敏感 RAG + 确定性约束。

首版重点指标包括：

- 最终决策正确率；
- 政策版本选择准确率；
- 必要工具召回率；
- 非法动作率；
- 重复副作用率；
- 平均工具调用次数；
- 延迟和 Token 成本。

Golden Cases 应覆盖正常流程、证据冲突、缺失数据、工具超时、政策版本边界、重复退款和越权诱导。

## V0.1 成功标准

首版成功不以页面数量或技术数量衡量，而以以下结果衡量：

- 至少一个案件能够完成调查、建议、审批、执行和验证闭环；
- 每个关键结论都有证据与政策引用；
- 错误输入、工具异常和模型异常不会产生伪成功；
- 自动化测试可重复运行且默认不调用真实模型；
- Demo 能清晰展示案件、证据、调查过程、建议、审批和 trace；
- 有可复现的评测结果和失败案例；
- 项目维护者能解释核心设计及其取舍。

## V0.1 非目标

当前明确不做：

- 通用聊天助手；
- PDF 聊天或普通企业知识库；
- 无边界的多 Agent 协作；
- 长期用户 Memory；
- 自动发送真实退款；
- 完整生产级电商平台集成；
- 为展示技术而接入大量 MCP Server；
- 微服务、Kubernetes 或复杂分布式基础设施。

## 后续技术的引入条件

- **MCP**：当只读调查工具已经稳定，且确实需要标准化接入或展示工具互操作性时加入。
- **LangGraph**：当审批中断、checkpoint 和长流程恢复已经成为实际需求时加入。
- **PostgreSQL/pgvector**：当数据规模、部署或检索需求超过 SQLite/NumPy 时加入。
- **Docker**：本地版本跑通并进入可复现部署阶段后加入。
- **可观测性平台**：已有稳定 trace 和评测数据后，再接入 Langfuse 或 OpenTelemetry。
- **多 Agent**：只有与单 Agent baseline 对比后出现可量化收益时才实验。

## 实施节奏

- 10–15 个有效开发日：形成可公开演示的 V0.1；
- 4–8 周：补齐评测、可靠性、部署和差异化实验；
- 每个阶段均遵循“学习当前所需知识 → 立即实现 → 验收 → 再进入下一阶段”。

范围、架构或项目目标发生变化时，应更新本文档。早期设想与后续决策冲突时，以最新确认并写入本文档的决定为准。
